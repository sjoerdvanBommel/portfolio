## What is a module?

People tend to be scared when they hear the word "module",
because of the complexity of the module **system** in JavaScript.
But a module itself is just a _self-contained_ piece of code.
It does not rely on anything outside of it. Here are some examples of modules:

<CodeBlock
  files={[
    {
      name: 'add.ts',
      content: 'const add = (a: number, b: number) => a + b;',
    },
    {
      name: 'calculator.ts',
      content: `class Calculator {
    add(a: number, b: number) {
      return a + b;
    }
  }`,
    },
  ]}
></CodeBlock>

But what if I want to use the `add` function from `add.ts` in `calculator.ts`?
This is where terms like `import`, `export` and `require` come into play. But these terms are not part of a module. This is instead part of the module _system_.

Without a module system, I would have to come up with my own solution, like copy-pasting
the `add` function into `calculator.ts`. But that would become a mess very quickly.

  <TimelineEntry title="JavaScript is born" emoji="👶" date={new Date("1995-01-01")}>
      JavaScript, or LiveScript at the time, was created at Netscape Communications by Brendan Eich in 1995.
      It was initially created to be a scripting language for their own browser, Netscape Navigator.

      <img src="/img/netscape-navigator.webp" alt="Netscape Navigator" className="my-4" />

      The language was in no way designed to be a general-purpose language for both client and server.
      It contained notable performance and security issues and _did not have any module system_.
      People used JavaScript because other browsers started to support it as well.
      There was no real alternative.
      <br />
      But if there is no module system and copy-pasting is not a scalable option, then how would you organize your code?
      Because JavaScript only ran in the browser back then, one possible solution was to create multiple script tags in the HTML file:

      <CodeBlock
        files={[
          {
            name: 'index.html',
            content: `<!DOCTYPE html>

<html>
  <head>
    <title>Script Order Example</title>
  </head>
  <body>
    <div id="userProfile">Loading user data...</div>

    <script src="api.js"></script>
    <script src="ui.js"></script>
    <script src="main.js"></script>

  </body>
</html>`,
          },
          {
            name: 'api.js',
            content: `function fetchUserData() {

// In real code, this would be an actual XMLHttpRequest
// (fetch didn't exist back then)
return {
name: "John Doe",
email: "john@example.com"
};
}`,
          },
          {
            name: 'ui.js',
            content: `function updateUserProfile() {
const userData = fetchUserData();
const profileDiv = document.getElementById('userProfile');
profileDiv.innerHTML = \`

<h2>\${userData.name}</h2>
<p>\${userData.email}</p>
\`;
}`,
          },
          {
            name: 'main.js',
            content: `// Try to update the profile as soon as the page loads
updateUserProfile();`,
          },
        ]}
      ></CodeBlock>

      In this example, we have a user profile section that starts with "Loading user data...". The `api.js` file defines a function to fetch user data, `ui.js` defines a function to update the profile with this data, and `main.js` tries to use this function immediately. If we load the scripts in the wrong order, we'll get errors because:
      - `main.js` tries to use `updateUserProfile()` before it's defined
      - `ui.js` tries to use `fetchUserData()` before it's defined

      This is why the order of script tags is important - they are executed in the order they appear in the HTML, and dependencies need to be loaded before they're used.
