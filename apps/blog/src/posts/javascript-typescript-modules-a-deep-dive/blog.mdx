## What is a module?

People tend to be scared when they hear the word "module",
because of the complexity of the module **system** in JavaScript.
But a module itself is just a _self-contained_ piece of code.
It does not rely on anything outside of it. Here are some examples of modules:

<CodeBlock example="javascript-typescript-modules-a-deep-dive/2-simple-modules" />

But what if I want to use the `add` function from `add.ts` in `calculator.ts`?
This is where terms like `import`, `export` and `require` come into play. But these terms are not part of a module. This is instead part of the module _system_.

Without a module system, I would have to come up with my own solution, like copy-pasting
the `add` function into `calculator.ts`. But that would become a mess very quickly.

<Timeline>
  <TimelineEntry title="JavaScript is born" emoji="👶" date={new Date("1995-01-01")}>
      JavaScript, or LiveScript at the time, was created at Netscape Communications by Brendan Eich in 1995.
      It was initially created to be a scripting language for their own browser, Netscape Navigator.

      <img src="/img/netscape-navigator.webp" alt="Netscape Navigator" className="my-4" />

      The language was in no way designed to be a general-purpose language for both client and server.
      It contained notable performance and security issues and _did not have any module system_.
      People used JavaScript because other browsers started to support it as well.
      There was no real alternative.
      <br />
      But if there is no module system and copy-pasting is not a scalable option, then how would you organize your code?
      Because JavaScript only ran in the browser back then, one possible solution was to include multiple `<script>` tags in the HTML file:

      <CodeBlock
        example="javascript-typescript-modules-a-deep-dive/3-multiple-script-tags"
        initialFile="index.html"
      />

      In this example, we have a user profile section that starts with "Loading user data...".
      The `api.js` file defines a function to fetch user data, `ui.js` defines a function to update the profile with this data, and `main.js` tries to execute this function immediately.
      <br />
      This looks somewhat like a self-made module system (although it is not). It comes with several drawbacks, with some of the most important ones being:
      1. The scripts are loaded in the order they appear in the HTML file. If we'd load `main.js` first, we'd get errors because `updateUserProfile()` is not defined yet.
      2. There is no explicit dependency management. Just from looking at `main.js`, there is no way to tell if it will work or not,
      because it depends on other files which are not explicitly referred to here. Tooling like ESLint or going to the source code of another script won't work either because of this reason.
      3. We might create naming conflicts in the global scope when we load multiple scripts which define the same variable.

      <br />
      There was no direct solution for the first two problems. However, they managed to limit the pollution
      of the global scope using a technique called "Immediately Invoked Function Expression" (IIFE).
      Since a function creates its own scope, they figured that they could use a function to create a new scope for each script.
      This way, variables and functions defined in one script would not be accessible in another:

      <CodeBlock
        example="javascript-typescript-modules-a-deep-dive/4-variables-in-functions"
      />

      However, because these files are now only defining functions, nothing will get executed.
      To fix this, we need to call the functions immediately when creating them (hence the name "Immediately Invoked Function Expression").
      By converting the function to an expression using parentheses, we can call it immediately and remove the function name:

      <CodeBlock
        example="javascript-typescript-modules-a-deep-dive/5-iife"
      />

      Now that all variables and functions are defined inside of this global function scope, we can decide ourselves what should be "exported" and what shouldn't,
      by returning the exports from the function:

      <CodeBlock
        example="javascript-typescript-modules-a-deep-dive/6-assign-to-global"
      />

<br />
This is definitely an improvement, but it only partially solves the problem. Other problems like the order of execution
are still present as well. Hopefully, it is clear why this is not a good long-term solution for such a big programming language as
JavaScript.
